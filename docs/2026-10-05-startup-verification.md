# 酒馆启动优化与验收

本轮基于聊天完善提交 `135d943`，仅在 `codex/sillytavern-startup` 独立工作区修改。生产服务器未访问、部署或重启；没有读取既有聊天、账号配置或密钥。原主仓库、performance 和 lifecycle 三个工作区保留。实验监听 `127.0.0.1:8772`，通过 `npm run perf:lab` 或 `start-lab.cmd` 启动，所有测试数据人工生成。

## 最终行为

- Transformers 与 Vectra 按需加载；并发首次调用共享依赖导入，Transformers 配置完成后才发布。保留公开 API 的异步签名、模型选项、图片错误返回 null、向量 HTTP 状态与索引内容。
- 前端缓存身份包含配置、package、可选 package-lock/npm-shrinkwrap 的原始字节及 Webpack 版本。缺失锁文件有明确 absent 身份，合法无锁安装可以构建。后端提交不再单独改变前端缓存目录。
- 每次启动仍运行真实 Webpack 校验，不按“输出存在”直接跳过。旧目录移入 `_webpack/.recycle`；已有回收区保留，回收继续占磁盘。
- 编译、stats 和关闭错误均拒绝启动，并关闭编译器。真实前端编译失败不监听端口，经过原异步刷写流程自然退出 1；正常关闭仍退出 0。

## 时间与等价性

计时使用新进程开始到 `/csrf-token` 首次返回有效 token，随后验证 `/lib.js`。Windows、本机 Node 24.15.0、同一个 startup 工作区与人工数据、已有文件系统缓存、顺序运行，分别取三次。

| 指标 | 基线 | 优化后 |
| --- | ---: | ---: |
| 三次 HTTP ready / ms | 4026.7 / 4029.9 / 4026.8 | 3305.0 / 3288.1 / 3295.4 |
| 中位数 / ms | 4026.8 | 3295.4 |
| 减少 | — | 731.4 ms / 18.16% |

Node 20.20.2 优化后另测三次为 4026.6 / 3826.4 / 3863.6 ms，中位数 3863.6 ms；没有同路径、同环境的 Node 20 前后对照，因此不对它声称加速比例。同一个 C 盘工作区的上述 9 次计时前端库均为 1,947,076 字节，SHA-256 为 `de3c3f6c415e86f431b10597bc753d44f9ca213fa3a20abaaf9ddac939ff416b`。F 盘独立基线用于浏览器功能比较，其输出字节不同，不作为逐字节兼容证据。

首次基线空缓存观测 32.47 s，优化后新缓存观测 11.33 s；两者操作系统文件缓存和初始内容状态不同，不能把这两数计算为冷启动加速比例。首次编译仍然耗时；较主要的长期收益是后端更新后可以保留经过 Webpack 校验的缓存。

真实本地 3×2 人工 PNG 逐像素等于旧实现，首次调用约 336 ms、暖调用约 16 ms（单次观察）。这是按需加载的首用代价，不是模型推理或通用图片吞吐结论。

## 验证证据

- `npm run test:perf`：Node 24 / Node 20 各 122 PASS、0 fail、0 skip；含原 94 项回归、新 8 项依赖导入、19 项构建缓存、1 项真实整应用失败退出。
- RED：依赖延迟 7 fail；缺失锁文件 3 fail；完整应用前端编译失败退出码原为 0、期望 1。另从原 `.bak` 源码重放带回收适配器的构建 RED，确认不是用修改后源码伪造失败证据。
- 实际 Webpack 覆盖暖输出一致、入口脏修改、正常版本更新的依赖、缺失/损坏输出、缺包错误、关闭失败、可选锁出现/缺失和 dist 路径选择。
- 两类 tokenizer 用随源码附带的模型验证真实编解码；每类 50 次冷并发 + 5 次暖编码 + 5 次解码，输出与冻结基线一致，初始化一次。
- 10 份改动 JavaScript 的 Node 语法检查通过。ESLint 未能运行，白名单源码副本没有其配置文件；未编造 lint 通过或新增临时产品 lint 规则。
- 三个原工作区共 3,455 份跟踪源码、HEAD 和状态，以及 9 份 `.bak` 指纹，前后全部一致。

Chrome 154 实际浏览器在基线/优化版各打开两次，人工角色列表、4 条消息保存与读取、CSRF、设置持久化和二次无 onboarding 均通过，无生成请求。每版两条原始页面错误都由 st-memory-enhancement 更新 manifest 被离线边界拦截产生；精确 URL、插件 stack、对应失败 fetch 和实际拦截联合验证，原始错误完整保留，unexpectedPageErrors=0。JS Slash Runner 也有后台外网更新检查，但没有将任意 Failed to fetch 宽泛忽略。

最后两次打开的 APP_READY 相对导航时间，基线约 4070 / 4086 ms，优化版约 4125 / 4022 ms，不能声称浏览器页面加载已提速。服务启动和浏览器加载是不同阶段。桌面/手机截图、所有失败与成功记录及 Git 提交后缓存复用验证见 F 盘最终交付报告。

## 局限与剩余问题

没有测线上 Linux、真实用户数量、Docker 启动、完整全局 npm 安装或真实生成模型；forceDist 只验证路径分离，无锁安装用人工项目的实际 Webpack 构建验证。Webpack 对 managed node_modules 仍假定相同包版本内容不变，手工同版本改包不在保证范围。

依赖导入重试测试注入的是可恢复解析失败。Node 可能缓存模块求值失败，ONNX 初始化失败也可能需要重启，不能承诺任意依赖故障都自动恢复。旧同任务 pipeline 冷并发、活跃任务 dispose、Vectra 独立索引实例并发写仍未修；server.js 顶层模块导入 catch 的退出状态亦未全面治理。

浏览器预装第三方插件有启动时外网更新检查，离线阻断会产生既存错误；本轮记录和归因，没有更改这些第三方源码。核心页面、人工聊天与二次打开的验证应和该网络边界分开解释。

第一次构建 RED 的旧 prune 永久删掉了两个纯人工缓存目录，未备份或恢复，不能声称其原文件的前后 hash 已核验。没有用户或既有数据受影响。后续失败重现加了仅移动的删除适配器，人工源字节与回收文件保留；事件详见 F 盘 `webpack-red-prune-incident.json`。

交付为独立本地分支、改动文件包、补丁与完整 Git bundle；不合并或部署。运行数据、配置、依赖、浏览器缓存与结果文件均在 Git 之外。
