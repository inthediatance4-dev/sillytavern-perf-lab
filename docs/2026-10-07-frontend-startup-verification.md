## 问题和实现

阶段探针发现，网页打开约 4 秒后触发 APP_READY，其中扩展加载占约 1.9 秒。扩展有先后关系和激活钩子，因此保留顺序执行，仅把已知内置 HTML 模板的读取提前并行发出。早期 JavaScript modulepreload 实验收益很小，已退出最终实现，代码和测试保留在 F 盘回收目录。

`public/scripts/templates.js` 增加 `preloadTemplates(paths)` 和共享的进行中请求表。编译函数进入原来的模板缓存；每次渲染仍单独应用调用数据、DOMPurify 和语言处理。50 个同时发生的冷异步渲染共用一份读取与编译函数。预取错误不弹提示，正常渲染错误保留原有提示和返回行为，失败可以重试。同步调用继续回退到原接口；晚到的异步结果不会替换已填入缓存的同步结果。

`public/scripts/extensions.js` 为 translate、connection-manager、regex、attachments、caption、expressions、memory、stable-diffusion、tts、assets、vectors 中的 16 个启动模板发出可选预取。预取使用实际包装接口的 `scripts/extensions/...` 缓存键，过滤已激活、禁用、版本不符、缺模块或缺依赖的扩展。顺序激活时再次检查条件，保留较早钩子对后续启用状态的影响。第三方模板路径不在列表内。

运行入口只调整隔离端口为 8773，并把新增测试纳入 `test:perf`。没有改检测算法、聊天格式、后端路由或扩展执行顺序。

## 性能结果和限制

测量点为导航时间原点到 APP_READY，双方均关闭首次引导，使用相同发行默认配置和插件组合。每种情况使用三个新的 Chrome 上下文，且没有同时运行回归测试。

| 情况 | 三次原版 APP_READY / ms | 三次新版 APP_READY / ms | 中位数变化 |
| --- | --- | --- | --- |
| 本机直接访问 | 4091.8 / 4044.6 / 4064.7 | 3997.0 / 3978.4 / 4105.2 | 4064.7 → 3997.0，约 1.7% |
| CDP `latency: 40` 模拟 | 8425.9 / 8469.5 / 8477.9 | 7853.6 / 7711.0 / 7731.2 | 8469.5 → 7731.2，约 8.7% |

模拟实验双方都使用相同 Playwright HTTP 响应替换流程，仅交换 `extensions.js` 和 `templates.js` 的原版/新版文本；没有阶段探针重写。按新版三次、原版三次的顺序运行，不能排除所有时间顺序和测量工具影响。CDP 的 `latency` 参数不是生产 RTT 的实测值，也没有模拟限速、丢包或真实用户数据量。

模拟实验双方每次均观察到 407 个资源和同样 16 次扩展激活，包含 21 个扩展 HTML 请求；没有把早期缓存键错误带来的 16 个重复请求留在最终实现中。本机原版早期资源探针使用默认 250 条缓存，不能用它与新版 407 条直接比较请求总量；APP_READY 事件时钟不受这一统计上限影响。

本机直接访问差异很小，且三次样本不足以证明稳定收益。模拟延迟下减少约 738 ms 是本轮有条件的实测结果，不外推到线上，不与上一轮服务监听启动的 18.16% 混为一个比例。此前空缓存、首次使用可选模型、真实生产重启均不在这个比较内。
