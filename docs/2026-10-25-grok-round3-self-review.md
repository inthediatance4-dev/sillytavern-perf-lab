# Grok round-3 self-review (2026-10-25)

> Historical review, superseded by [the locking simplification](2026-10-26-locking-simplification.md).
> The per-path cross-process protocol, its flags, storage namespaces, parent
> filesystem fences, acquisition gates, and protocol-only tests described below
> have been deleted. These are historical findings and test results, not current
> guarantees. Current locking uses the data-root owner lock and in-process queues.

Reviewed `git diff a73dd78..HEAD` on `codex-improvements` before the fix commit: `7680483` (pid-reuse identity) and `73269ac` (opt-in cross-process exclusive path locks). No push. Tag `grok-handoff-start` and branch `backup-before-grok-r2` were not moved. The nested-lock fix is option (a): while an exclusive cross-process file is held, `withPathLocks` refuses another entry, and the backup writer acquires the backup directory only after that file is released. A global sort of keys acquired by later nested calls was not used. Those calls no longer run while the outer files are held.

## Checked, not defects

- **Lock order inside one reservation.** `normalizeLockRequests` still sorts every key before any wait. `acquireExclusivePathLocks` (`src/path-fs-lock.js`) takes that sorted list one key at a time and releases any prefix if a later key throws (`:476`). The inversion was only across a nested `withPathLocks`. That path is closed above.
- **Shared to exclusive upgrade.** A nested exclusive request for a key this stack holds shared or exclusive rejects with `lock_reentered` before `reserve` (`src/chat-io.js:217`). No gate count is leaked. Regression: `tests/path-fs-lock.test.mjs:364`.
- **Filesystem lock leak on rejection or timeout.** `acquireExclusivePathLocks` releases keys already taken when a later key fails. `withPathLocks` assigns `fsHeld` only after that returns, and its `finally` releases those files and then the in-process gates, including when the task throws. A nested `lock_reentered` returns before `reserve` and before any file is created. Regression: `tests/path-fs-lock.test.mjs:341` and `:364`.
- **`waitForChatIO`.** The reservation is added to `pendingIO` synchronously before `withPathLocks` returns (`src/chat-io.js:264`). The filesystem wait sits inside that same promise, so a waiter blocked on another process is included. `waitForChatIO` (`:630`) drains the set.
- **`path_lock_busy` timeout.** `acquireOne` tries to create, then reclaims a stale file, and only then compares `Date.now()` with the deadline (`src/path-fs-lock.js:455`). A holder that releases during the sleep is observed on the next create. A holder that releases after the deadline check and before the throw can produce one `path_lock_busy`; the files this attempt took are released, and a later attempt can acquire. Not a leaked lock.
- **Reclaim of dead or reused holders versus live ones.** `classifyPidLiveness` (`src/process-identity.js:257`) returns `dead` on `ESRCH` and `live` on an unknown signal error. A live pid whose boot id or process start differs is `reused` and may be removed. A live pid whose recorded boot id and process start still match is kept, including `EPERM`. A payload with neither identity field is kept while the pid is alive (`:263`) and reclaimed when the pid is dead. Another host is left in place (`src/path-fs-lock.js` `classifyPayload`, and the same rule in `src/data-root-owner.js` `inspectLock`). Regressions: `tests/path-fs-lock.test.mjs:294` and `tests/data-root-owner.test.mjs` (identity fields, reused pid, matching identity, no identity, `EPERM`, two-process reclaim).
- **Windows path length and hashed names.** `exclusiveLockPathFor` (`src/path-fs-lock.js`) names the file `<sha256>.lock` under `<root>/.st-path-locks/`, so the target path is not a path component. The payload no longer has to contain that path. See the P2 row for the size cap.
- **Old lock payloads without identity fields.** Covered by `classifyPidLiveness` above. Data-root records that predate `bootId` / `processStartMs` stay fail-closed while the pid is alive. `token` is optional on read (`src/data-root-owner.js` `classifyOwner`). Path-lock files from `73269ac` always had `key`; `keyHash` is an additional accepted form.
- **Enable failure at startup.** `configureCrossProcessPathLocks` sets `enabled` only after the root is resolved (`src/path-fs-lock.js:89`). A throw leaves `enabled` false. `src/server-main.js:118` catches that, warns, and continues with in-process locks. If `exclusiveDataRoot` already acquired the owner file, that owner lock stays; path locks do not turn on. That is the degradation the startup comment describes, not a half-enabled path-lock flag.

## Residuals (not P1/P2, no code change)

- Shared holders still do not create cross-process files (`src/chat-io.js` `chatLockPaths`). An exclusive directory operation in one process and a file operation in another do not conflict on the filesystem, because the file operation's parent lock is shared and stays in-process. Atomic replacement still covers readers of a finished file. Directory rename or delete against a writer in another opted-in process is outside this lock set. A shared filesystem lock would be a new protocol; it was not added.
- On Windows, `win-boot:` comes from `Date.now() - os.uptime()` and a step larger than 2 seconds can look like pid reuse (`src/process-identity.js` `bootIdsMatch`). A missed or slow process-start probe omits `processStartMs` and then fails closed. Linux boot id and `/proc/<pid>/stat` starttime do not use that approximation.
- The lock file path is the data root plus `.st-path-locks/<64 hex>.lock`. A data root already within about 80 characters of `MAX_PATH` can still fail to create the lock file. The failure is `path_lock_unavailable`, and no file is left behind.
- An existing oversized, symlink, or non-file lock is refused and left in place. New writers do not create the oversized case.
- In-process nesting of a different key remains when cross-process locks are off. Nothing in production holds the backup directory and then takes a chat path. The backup writer still nests only in that in-process sense; it does not nest filesystem locks.
