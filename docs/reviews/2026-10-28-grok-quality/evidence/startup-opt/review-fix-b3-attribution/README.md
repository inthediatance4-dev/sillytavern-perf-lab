# Review-fix B3：T_ui / T_send 归因更正

依据：`../p2-ac-ab/s3-bwarm/comparison.json`（S3 B-warm，base=`9360604`，head=P2-a+P2-c，n=12/边）与 `../p0-baseline/s3-bwarm/`（同一产品代码，n=20）。

## 更正后的结论

T_ui、T_send 都从 T0 起算。P2-a 只改服务端，能解释的部分只有 T_http 的缩短：

| 指标 | base → head 中位 ms | Δ | 95% CI | 归因 |
|---|---|---:|---|---|
| T_http | 1432 → 629 | −803 | [−1463, −392] | **P2-a**（Webpack 815→35，CI [−1290, −715]） |
| T_ui | 4405 → 2873 | −1533 | [−2375, −157] | 约 **800ms 来自 T_http**；其余约 730ms **原因待查** |
| T_send | 5238 → 3587 | −1651 | [−2499, −115] | 约 **800ms 来自 T_http**；其余约 850ms **原因待查** |
| ui − http | 2613 → 2249 | −363 | [−959, 501] | 未证明 |
| send − ui | 774 → 723 | −51 | [−250, 39] | 未证明 |

## 为什么不能把 −1.5 s 全算给 P2

同样的产品代码，ui − http 在 P0 基线里中位数是 2174ms，在这次 A/B 的 base 侧是 2613ms，head 侧是 2249ms，和基线接近。也就是说，多出来的差距主要是 A/B 那次 **base 的前端段变慢**，不是 head 的前端变快。

可能原因（都没验证）：

1. 测量时段之间的漂移（长聊天优化时也出现过）；
2. base 每次启动都要编译，Webpack 编译完成后在后台把缓存写盘，和浏览器加载抢 CPU；head 跳过编译，没有这部分后台工作。如果属实，这也是 P2-a 的真实收益，S1（更新后第一次启动）也会受影响。

验证方法（下一轮做，不阻塞合并）：在 base 的 ui 阶段采集服务端进程 CPU 占用。

本轮总结只引用：**T_http −803ms（P2-a）**，以及 **T_ui / T_send 中由此带来的约 800ms**。
