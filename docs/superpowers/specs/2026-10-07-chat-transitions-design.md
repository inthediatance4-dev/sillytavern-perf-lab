# Chat navigation responsiveness

The user reports that entering and leaving chats on the deployed SillyTavern is sluggish. They authorize autonomous isolated improvement. Earlier explicit instructions and the project agreement forbid deployment or service restart without explicit authorization. Existing data stays protected; no deletions outside Recycle, no real chat bodies or secrets in evidence.

## Verified baseline

Production runs SillyTavern 1.18.0, Node 20.20.2. Nine core files plus group-chats.js and templates.js match the original imported commit db53872. Two third-party extension files differ and must be preserved. The latest experimental branch b14fefec is not deployed. Production file statistics show 11 chats, about 44.5 MB total, largest about 15 MB; only sizes and necessary numeric UI preferences were inspected.

Artificial Chrome navigation, using the verified original frontend against the isolated lab backend, loads the default 600-message chat (about 7.5 MB) before the requested 180-message chat (about 0.2 MB). Two desktop samples take 6.45–6.58 seconds; CPU-rate-4/mobile-viewport samples take 8.18–8.31 seconds. The measurements include awaited extension events and two animation frames, not GPU frame rates. Original backend /recent tests with 11 artificial files, 43,181,780 bytes, reread all eleven files on every request: 66 streams and 259,090,680 bytes over six requests. Warm request times are 36–47 ms on this computer; these are not production-server timings.

## Independent change A: open the requested chat once

Extend selectCharacterById options with optional nonempty string chatFile. Legacy calls preserve their existing flow, including switchMenu. The targeted mode reports whether selection was accepted so the welcome caller cannot save an active character after a rejected switch. Existing save/generation/id guards stay effective; targeted mode also refuses during character generation. When changing characters, clear existing chat state and establish the target character as before; unshallow before assigning any filename, then use the existing openCharacterChat path for a different requested chat. If the requested file is the character's default, load it once using getChat. Same-character selection never reloads an already open file, but opens a different file normally. Preserve metadata, selected_chat_pole, character persistence, awaited CHAT_CHANGED ordering, normal error handling and TTS/edit cleanup. Avoid intermediate default-chat events and rendering. Preserve legacy void-return semantics when no chatFile option is passed if practical.

The welcome recent-character entry passes chatFile to this function and only updates active-character/settings after successful accepted selection. Serialize concurrent recent-character clicks with a small scoped busy flag released in finally; ignore repeated taps during the pending navigation. Do not introduce an application-wide navigation framework, change group-chat selection, unawait extension hooks, disable plugins, or alter the user's UI preferences.

Tests execute the actual selectCharacterById/openRecentCharacterChat source with only I/O/UI boundaries stubbed. Cover one load and one CHAT_CHANGED for the requested file, default target, legacy selection, shallow-card refresh, same-character different/same file, invalid id, saving, group and character generation, persistence, rejected selection, error cleanup, and overlapping recent clicks. If another navigation changes the active character during an awaited preparation, do not open or persist the target on that other character.

## Independent change B: bounded recent-chat metadata cache

Add src/chat-info-cache.js exporting createChatInfoCache(readInfo, options) and a getter(path, additionalData, withMetadata). readInfo receives path and boolean metadata and calls the existing getChatInfo(path, {}, metadata) with no matcher. Integrate only the /recent route. Keep searches, general getChatInfo and chat writes unchanged. Preserve recent sorting, pins, limits, schema, metadata flag and group/avatar annotations.

Cache by resolved file path and metadata mode. Validate each hit using a fresh stat identity (device, inode, size, nanosecond mtime and ctime on Node 20+). On misses, read normally and stat again; cache only successful stable snapshots. Stat/read failures must propagate and never poison a later retry. Coalesce identical in-flight versions, without letting older operations delete or replace newer pending records. Pending records, entries, and estimated bytes are all bounded; excess concurrency reads uncached. Defaults: 256 entries, 8 MiB estimated retained bytes, 512 KiB maximum estimated per entry, 60-second absolute TTL. Prune expired records on access; this is not an idle purge promise or an exact heap-byte ceiling. Estimate JSON byte length conservatively plus path/object overhead. Skip oversized entries, do not truncate last messages. Clone stored values and every result; apply caller-specific annotations after cloning. Different user roots and metadata modes must remain isolated. No disk persistence, logs of metadata values, background timer, new dependency, configuration UI or schema migration.

Tests use real fs and HTTP /recent, plus controlled injected reads/stat/clock for races and deterministic resource limits. Prove a second unchanged request opens no streams, rewritten/atomic-replaced same-size files invalidate even if mtime is restored, changed-during-read snapshots are not cached, failures retry, coalesced waiters receive independent objects, extra data does not leak, metadata modes and user paths differ, malformed/empty reader output preserves existing semantics, eviction/TTL/large results/concurrency stay bounded, and pins/order/group annotations remain correct.
