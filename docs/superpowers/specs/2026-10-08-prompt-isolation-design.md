# Prompt cache ownership and persistence safety

Base d86a7b108e85ef1f69454bd86d3fe652028f4bec; branch codex/sillytavern-prompt-isolation; synthetic-only localhost8778. User delegates isolated decisions; no production access/deployment/restart. All explicit deletions must use Recycle Bin; preserve backups and failed evidence.

## Confirmed problem

Actual old loadItemizedPrompts awaits storage and then assigns the shared array/emits LOADED. Reversed completion replaces B with A; stale errors erase B. clearChat saves an empty cache over A before A finishes reading, then late A restores the closed cache. A clear awaiting setItem can later empty B's newly loaded array. Four source-function reproductions are in external baseline-race-reproduction.json. Existing356 baseline tests pass and do not cover these internals.

## Decision and alternatives

Use module-local prompt request generations, readiness and optional caller ownership. Storage results stay local until checks pass. This avoids serializing slow reads ahead of current reads; IndexedDB/localforage cancellation is not required. Rebuilding storage or changing prompt schema is unnecessary. Preserve existing cache/store format, event payloads and successful legacy void return.

## Required behavior

1. Reserve an incoming prompt owner synchronously at character load entry, before unshallow/fetch and fresh greeting's saveChatConditional. The cache is unavailable for persistence until that owner's successful read. This prevents the save-before-read path too. Reserve group ownership before awaited preparation/fetch; late/same-file group requests must not supersede newer owners when they reach prompt loading. Capture group/chat identity, recheck selection and reservation before read and after await; handle legitimate chat-id initialization in validation.
2. loadItemizedPrompts(chatId, optionalOptions) accepts a prepared request and optional isCurrent predicate. One-argument calls create their own generation and still work. Check validity before starting/superseding a read, after storage success, before assigning/emitting, and in catches. Canceled reads return false, with no cache mutation, LOADED or stale error logging. Normal successful calls remain undefined and emit {chatId}. Absent storage returns a READY empty array; no-id legacy call clears and supersedes earlier reads without LOADED.
3. A current storage rejection leaves an empty UNAVAILABLE cache; saves must not replace existing records with that incomplete state. Successful reload/retry restores readiness. Do not silently mark generated pushes ready after read failure; preserve stored data until successful reload, and document that new inspection entries may remain unpersisted during failure. Listener rejection after successful read must not erase valid loaded data or a newer cache; distinguish read failures from event failures.
4. saveItemizedPrompts must suppress persistence and SAVED while the shared cache is unavailable. READY cache may still save to arbitrary supplied filenames: bookmarks intentionally save-as. One-argument success/event payload remain compatible. Keep prior completed snapshot and filename separate from newer cache ownership during awaited persistence; do not cancel an already-started legitimate old-cache save merely because a later chat opens.
5. clearChat invalidates prompt reads immediately before awaits and captures a prompt-clear token plus its character-clear serial. After persistence, reset the cache only if its prompt token is still current; do not mutate a newly loaded exported array. Also avoid late clearData erasing a newer chat when ownership changed during the prompt save. Unready cache never overwrites a stored record on close. Clear invalidation covers legacy/group reads too.
6. Character getChatResult supplies its owner to the helper and stops on false before print/menu/events. Group loader stops on false before message/render/metadata continuation. Existing successful greeting, group/neutral, edits, swipes, message formatting, rendering scheduling and prompt schema are preserved. No generated model calls or storage deletion UI is exercised. Already-running third-party event internals cannot be aborted; unrelated generation/explicit-delete workflow races remain outside scope.
